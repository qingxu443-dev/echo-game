## 持续集成

`.github/workflows/suites.yml` 在每次推送到 `main` 和每个 PR 上复跑本文件的套件，Ubuntu 与 Windows 各一个 job。Windows job 存在的理由很直接：Windows 是人工验收平台，而此前它的入口守卫比 Linux 少。

**断言数不写死在 workflow 里**：CI 从 `tests/framework/baseline.json` 读取下限，脚本层面同样由 `tests/run_suites.gd` 从那里取值。实跑值低于下限直接退出 1；高于下限只打印提示，因为那是覆盖增加，不需要任何分支改共享文档。

**文档不再复制可变数字**：README、ARCHITECTURE、PROJECT_STATUS 与 TESTER 一律不写当前套件数、断言总数或模块行数。`ARCHITECTURE.md` 的模块表只保留职责与约束，行数上限由 `doc_checks.gd` 的 `module-lines` 守卫按真实文件直接检查。此前四份文档各自抄一份数字，每个 PR 都改同一批行，最终演变成反复的合并冲突；现在只有这一份机器文件会在下调时改动。

**一份实现，三个入口**：`tests/run_suites.gd` 持有全部守卫（脚本错误、断言下限、文档一致），`run_all.sh` 与 `run_all.ps1` 只负责找到引擎并启动它。此前两边各写一套等价逻辑，PowerShell 那份漏了 `SCRIPT ERROR` 与文档校验——于是 Windows 上的绿灯比 Linux 的更宽，而 Windows 恰恰是人工验收平台。

这条守卫是被三次漂移逼出来的：三个不同的 PR 各自把同一句"N 条断言"改成自己看到的数字，最后合并的那个赢，其余留在过时状态（最近一次是 `716` 与真正的 `752` 并存）。检查会跳过两类**正确但不等于基线**的数字——单个套件的断言数（如 `test_hunter_summon.gd` 的 39 条）与历史运行记录（归档、修复前）。

这条守卫是必需的：某个套件走到不存在的调用会**中途报错但整体仍退出 0、failures=0**。

因此测试运行器还会直接拦截脚本错误：只要某个套件的输出里出现 `SCRIPT ERROR`，该套件记为 broken 并让整轮退 1，不再需要等断言数下降才发现。断言数守卫则继续拦住「少跑了几条但没错」的情况。

## 如何复现

```sh
# 全部套件 + 汇总
tests/run_all.sh                       # bash
tests\run_all.bat                      # Windows 双击或 cmd

# 单个套件
godot --headless --path . --script res://tests/test_core_rules.gd
```

每个套件结束会打印一行机器可读结果：

```
RESULT test_core_rules assertions=18 failures=0
```

`run_all` 汇总 `assertions` 与 `failures`，任一非零即返回非零退出码。
