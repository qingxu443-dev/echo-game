> 状态：Phase 0 工作规范  
> 目标：Prototype 0.1  
> 分支：`prototype/0.1`  
> 本文档将已确认规则与建议时序、待决问题分开。建议时序在被明确接受前不是已批准的玩法规则。

> **现状核对（2026-11-25，`main` @ `aa569bd`）**：本文档为 v0.1 规范的忠实翻译。第 14 节所列「实现前需决策」中的多数项目已在实现中收口：AP 在确认后、状态变更前扣除；移动为原子校验、全有或全无；敌方执行顺序为「动作优先级 → 稳定棋盘位置 → 稳定角色 ID」；伙伴已实现为猎人通灵（玩家动作窗口内下令、立即执行、不占 AP）；预告锁定模式采用角色/格子/区域混合模型。事件结算顺序已由 `docs/design/ECHO_SYSTEM_LAWS_v1.0_zh-CN.md` 补充「法则层」表述。现行实现的权威描述见 `docs/engineering/ARCHITECTURE.md`。

## 1. 目的

为战斗动作及其后果的结算定义单一、可检视的顺序，防止各系统以互相冲突的顺序独立地应用伤害、死亡、预告取消、状态效果、伙伴动作或回合切换。

本文档是设计与实现契约草案，不实现任何玩法代码。

## 2. 范围

### 包含

- 玩家动作的请求、校验、目标确认与执行
- AP 支付
- 移动与攻击的结算边界
- 伤害与死亡处理
- 敌方预告的创建、取消与执行边界
- 伙伴指令与支援动作边界
- 回合结束与战斗结束检查
- 事件记录要求

### Prototype 0.1 排除

- 局内经济与章节推进
- 回响契约与世界观基调修饰
- 收藏与广域状态叠层联动
- 完整局外成长与解锁系统
- 局内存档、检查点或断点恢复

## 3. 已确认规则

以下为已确认的项目规则，不得悄悄更改：

1. 战场为正方形网格，移动仅限正交方向；不允许对角移动。
2. 原型移动消耗 1 AP，最多移动两格。
3. 玩家回合基础预算为 3 AP。
4. 墙体、障碍与其他单位阻挡移动。
5. 回合结束时清空未用 AP。
6. 动作立即结算。玩家仅可在目标确认前取消；已执行的动作不可撤销。
7. 敌方预告在玩家回合开始时生成。
8. 敌方执行遵循对玩家清晰可见的固定顺序。
9. 敌人阵亡时其预告立即取消。
10. 原型阶段的伙伴动作由玩家下令、随后自动执行。伙伴在每个玩家回合拥有一次独立支援动作，不消耗玩家的 3 AP。
11. 伙伴拥有独立生命，可被攻击或击败。
12. 无局内存档、检查点或断点恢复。仅局外进度可以持久化。

## 4. 建议的动作生命周期

以下生命周期是供评审的建议技术时序。它不解决「控制与预告交互」等尚未收口的玩法结果。

### 4.1 玩家动作

1. **输入** — UI 发送包含单位、动作定义与预期目标/终点的动作请求。
2. **校验** — 权威战斗规则检查单位状态、可用 AP、射程、直线/路径合法性、目标有效性及其他动作要求。
3. **预览** — UI 展示已校验的目标/射程结果。预览不得改动战斗状态、不得消耗 AP。
4. **确认边界** — 玩家确认动作。仅允许在此边界之前取消。
5. **支付消耗** — 动作的 AP 消耗一次性扣除。校验失败则不消耗 AP。
6. **结算动作** — 权威动作结算器应用移动、攻击或技能效果。
7. **结算后果** — 按已批准的事件顺序处理由此产生的伤害、击败、预告生命周期变更与符合资格的触发。
8. **刷新表现** — UI 读取权威状态并更新 AP、单位、预告与反馈。
9. **检查战斗结束** — 在该动作的后果结算完成后评估胜负条件。

**实现待决问题：** AP 在动作状态变更的前一刻还是后一刻扣除。上文建议在成功确认后、结算前扣除，使动作不付费就无法执行。写代码前需要批准。*（现状注：实现采用「确认后、状态变更前」扣除，见 `scripts/battle/ap_budget.gd` 与 `skill_executor.gd`。）*

### 4.2 失败或取消的动作

- 目标确认前取消的动作不得改变战斗状态、不得消耗 AP。
- 非法的动作请求不得改变战斗状态、不得消耗 AP。
- 已跨过确认边界的动作不可撤销。
- 错误反馈应解释动作为何不可用，但不暴露内部实现细节。

## 5. 建议的移动结算

1. 校验完整请求路径。
2. 拒绝对角、被阻挡、越界或其他非法移动。
3. 确认移动并支付 1 AP。
4. 沿已接受的路径移动单位。
5. 发布移动后的位置。
6. 仅当当前原型规则存在移动触发效果时，结算这些效果。
7. 若移动可能导致相关终止条件，检查战斗结束条件。

**待决：** 移动是否始终为原子（全部请求格或全不执行），或可在最后一个合法格停下。建议的原型基线：原子校验、全有或全无，以避免模糊的部分扣费行为。该建议当时未获批准。*（现状注：实现为原子校验、全有或全无。）*

## 6. 建议的攻击与伤害结算

一次已确认攻击的候选顺序：

1. 重新校验已提交动作的目标与必要条件。
2. 若已批准的战斗模型存在命中/未命中等攻击结果，先结算该结果。
3. 按已批准的伤害公式计算伤害。
4. 将伤害应用到目标。
5. 生命归零或更低时立即判定击败。
6. 若被击败的是敌人，标记击败并立即取消其预告。
7. 按明确定义的优先级结算已批准的命中/受击/击败/打断效果。
8. 刷新 UI 与事件日志。
9. 检查战斗结束条件。

**本文不决定：** 护甲公式、暴击、伤害取整、过量伤害处理、同时伤害、状态顺序，以及被击败单位能否产生已排队的触发。这些需要专门的战斗数学与事件优先级决策。*（现状注：伤害公式与结算顺序已分别在 `docs/design/combat_stats_zh-CN.md` 与系统法则文档中收口。）*

## 7. 敌方预告生命周期边界

已确认的生命周期事实：

- 预告在玩家回合开始时创建。
- 敌人阵亡时其预告立即取消。
- 敌方动作按固定且可见的顺序执行。

必须保持的不变量：

> 预告展示与最终的敌方执行必须源自同一份权威动作/意图定义。UI 不得自行重构敌方的攻击。

以下问题在当时仍待决，需在「敌方 AI 与预告系统」规范中收口：

- 目标在执行前移动。
- 目标离开预告区域。
- 成功的控制或打断。
- 失败的控制或打断。
- 先执行的敌方动作使后续敌方计划失效。
- 预告创建后的地形变化。
- 执行时已无合法目标或终点。
- 预告锁定到目标、格子/区域，还是一条重校验规则。

本文档不批准任何回退（fallback）行为。

*（现状注：以上各项已按 `docs/engineering/DECISIONS_AND_OPEN_QUESTIONS.md` 的「已确认规则」收口：角色/格子/区域混合锁定模型，失效即取消、绝不重选。）*

## 8. 建议的玩家回合与敌方阶段边界

当前已确认的高层流程：

1. 玩家回合开始；生成敌方预告。
2. 玩家在 3 AP 预算内行动。
3. 玩家结束回合。
4. 敌方按固定可见顺序执行。
5. 状态结算。
6. 开始下一个玩家回合。

更细的候选阶段划分：

### 玩家回合开始

- 将玩家 AP 重置为已批准的回合预算。
- 从敌方决策数据生成敌方意图/预告。
- 冻结并展示即将到来的敌方阶段的执行顺序。

**待决：** AP 重置、状态时长更新、伙伴支援可用性重置与预告生成之间的确切先后顺序。

### 玩家动作窗口

- 仅接受已校验的玩家动作。
- 保持既有预告稳定，除非已确认规则显式取消或更改其一。
- 不允许 UI 改动权威战斗状态。

### 玩家结束回合

- 清空未用 AP。
- 关闭玩家动作窗口。
- 开始敌方执行。

### 敌方阶段

- 按可见的固定顺序处理敌人。
- 每个敌人行动前，按最终批准的预告规则判定其单位与计划动作是否仍然合格。
- 用预告所用的同一份动作定义结算其动作。
- 若敌人轮到行动前阵亡，立即取消其预告。

合格性与回退规则当时待决；本文档不定义它们。*（现状注：实现为「不合法即取消并记录原因，绝不重选」。）*

### 回合结算与下一回合

- 结算已批准的阶段末效果。
- 评估胜负。
- 若战斗继续，开始下一个玩家回合并生成下一批预告。

**待决：** 阶段末效果发生在最终胜负检查之前还是之后。这必须与状态与事件优先级规则一同收口。

## 9. 伙伴动作边界

已确认：

- 玩家下达指令。
- 伙伴自动执行。
- 伙伴在每个玩家回合拥有一次独立支援动作。
- 该动作不消耗玩家的 3 AP。

当时待决：

- 伙伴指令是在玩家正常动作窗口内下达，还是通过独立的指令窗口。
- 伙伴指令在选定后、执行前能否更改。
- 伙伴执行相对于玩家动作与敌方预告的确切时机。
- 伙伴动作在玩家结束回合之前还是之后可用。
- 伙伴动作选定的目标失效时如何处理。

在这些决定获批前，代码不得假定最终的伙伴时机模型。

*（现状注：已实现为**猎人通灵**——玩家动作窗口内下达、校验后立即执行、不占 AP、两回合冷却、一击即走、不生成战场单位；目标失效时不造成伤害且不进入冷却。见 `docs/engineering/PROJECT_STATUS.md` 的 P0 与 `scripts/battle/summon_service.gd`。）*

## 10. 战斗结束结算

候选要求：

- 仅在当前原子动作及其必要后果结算完成后评估胜负。
- 终止结果一经提交，拒绝后续战斗动作。
- 结果只结算一次；重复的事件通知不得产生重复结算。
- 战斗终止后预告与已排队的敌方动作不得继续。

**待决：** Prototype 0.1 遭遇的确切胜负条件，以及双方在同一结算链中同时被击败时的优先顺序。

## 11. 事件与日志要求

每条权威战斗事件应至少可追溯：

- 战斗局内序号
- 事件类型
- 行动实体 ID（如适用）
- 目标实体 ID（如适用）
- 动作/意图 ID（如适用）
- 来源系统
- 结果摘要
- 相关状态变更引用

建议的事件类别（名称为临时方案）：

- `action_requested`（动作请求）
- `action_rejected`（动作被拒）
- `action_confirmed`（动作已确认）
- `ap_spent`（AP 已支付）
- `actor_moved`（单位已移动）
- `attack_resolved`（攻击已结算）
- `damage_applied`（伤害已应用）
- `actor_defeated`（单位被击败）
- `telegraph_created`（预告已创建）
- `telegraph_canceled`（预告已取消）
- `enemy_action_started`（敌方动作开始）
- `enemy_action_resolved`（敌方动作已结算）
- `companion_command_issued`（伙伴指令已下达）
- `companion_action_resolved`（伙伴动作已结算）
- `turn_ended`（回合已结束）
- `battle_won`（战斗胜利）
- `battle_lost`（战斗失败）

事件名称为实现建议，不是面向玩家的文案，也不是最终 API 名称。

## 12. 核心不变量

以下不变量应被强制执行并测试：

1. 被拒绝或在确认前取消的动作不消耗 AP。
2. 已确认的动作消耗消耗至多一次。
3. 同一动作不能因重复输入被执行两次。
4. 移动绝不穿过被阻挡格或对角边。
5. 被击败的敌人不能执行后续动作。
6. 被击败敌人的预告立即移除。
7. 预告展示与敌方执行共享同一份权威意图/动作定义。
8. 可见的敌方顺序与实际执行顺序一致。
9. 伙伴的独立支援动作不悄悄消耗玩家 AP。
10. 终止的战斗状态不接受后续战斗动作。
11. 不为恢复目的写入任何局内战斗状态。

## 13. Prototype 0.1 测试用例

- 确认前取消移动：位置与 AP 保持不变。
- 提交非法移动：位置与 AP 保持不变。
- 确认合法移动：恰好支付 1 AP，单位最多沿正交移动两格。
- 尝试穿过墙体、障碍或单位：移动被拒绝。
- 确认攻击：其 AP 消耗恰好支付一次。
- 在排定行动前击败敌人：其预告消失且不再行动。
- 完整跑一遍敌方阶段：执行顺序与可见顺序一致。
- 逐一比对每个普通敌人的预告与实际执行的目标、区域、伤害与效果。
- 下达伙伴指令：伙伴本回合最多执行一次支援动作，玩家 AP 不变。
- 触发战斗胜利或失败：结果只提交一次，后续战斗输入被拒绝。
- 反复完整游玩遭遇：不出现软锁、重复动作或陈旧预告。

## 14. 实现前需决策

以下决策应在 P0/P1 实现前评审批准：

1. AP 扣费相对动作结算的时机。
2. 请求路径被阻挡时，移动取原子还是部分执行。
3. 伤害/死亡/触发的确切优先级。
4. 预告的目标移动与离开区域行为。
5. 控制/打断的成功与失败行为。
6. 固定的敌方执行排序规则。
7. 后续敌方动作失效后的回退。
8. 预告生成后的地形变化行为。
9. 伙伴指令与执行的时机。
10. 阶段末状态结算与战斗结束检查的顺序。
11. 同时击败的优先顺序。
