# 存档边界全量检查与暂停保存修复

日期：2026-11-29。接续 main `95613be`（已包含 #126、#127、#128），实施分支 `fix/save-contract-audit`。本轮针对连续出现的合法数据误拒，检查项目全部持久化入口、跨场景交接与奖励事务。环境为 Godot 4.7.2 Standard / GDScript / Windows x86_64；玩法仍为春之境探索和单人上场、队伍轮换的战棋战斗。

## 玩家反馈结论

“保存并退出”失败可稳定复现，原因在数据转换边界。普通地图 JSON 把装备整数读成 float；前次规范化只处理队员槽位，遗漏当前穿戴和共享背包。进入下一场战斗时，这些遗漏的数值被复制回角色槽位，暂停快照的严格 int 校验拒绝保存。全部目录武器与护甲均能触发，与磁盘空间无关。

旧版 `SessionSave.write()` 校验失败直接返回 false，没有写失败原因；暂停菜单把所有失败统一提示成检查磁盘。因此现有日志未记录这次暂停校验的字段。此次定位依据为目录回归和最新玩家存档副本的真实场景回放，没有据提示文字推断磁盘故障。

玩家原始文件只读备份在本地忽略目录 `build/recovery-backups/pause-audit-20261129-002638/`，未加入 Git、未上传 PR、未改写原档。副本加载地图、进入遭遇、暂停保存并重建场景成功，暂停前后的角色状态逐字段一致。副本只能验证已落盘进度，无法取得旧程序尚未保存的内存动作。

## 缺陷与修复

| 严重度 | 位置 | 原因及影响 | 本轮改动与验证 |
|---|---|---|---|
| 高 | `scripts/battle/party_loadout.gd::canonical_json_carry` | 顶层穿戴和背包遗漏 JSON 整数规范化；从地图读档进入战斗后暂停保存失败，背包装备后也可触发 | 已将所有装备来源统一规范化，只转换有限、整值且可表示的已知整数字段；严格会话类型不放宽。遍历目录装备，覆盖地图磁盘往返、进入战斗、背包换装、切人、暂停和真实场景恢复 |
| 高 | `scripts/meta/communications_mail_service.gd::recover_transaction` | 邮件事务仅检查顶层 Dictionary 就覆盖残片库和邮箱，错误版本、坏嵌套、错误目标及领取凭证丢失均可能成为正式存档 | 写任何文件前统一验证两份镜像、版本和目标路径；领取记录的实例必须存在于对应库存；拒绝时两个原文件和事务日志均保留。故障注入逐字节检查，合法中断仍可恢复 |
| 高 | `scripts/meta/communications_mail_service.gd::claim_attachment` | 在日志与双文件写入前修改原附件；失败会提前显示已领取，持有旧数据的界面重试还可能重复生成奖励 | 使用附件副本，成功后才提交给调用者；恢复后重新读取持久领取记录。真实入口制造“库存已写、邮箱失败”，原内存不变，重试不重复生成且原实例与 revision 不变 |
| 中 | `scripts/fragments/fragment_store.gd::load_store/from_dict`、`fragment_catalog.gd::validate_module` | `int()` 截断接受小数版本、小数容量，字符串和 bool 被强转；负 revision 被静默改零 | 磁盘读档和事务预检共用无副作用 `from_dict`；元数据要求有限整值、正确版本及非负 revision；容量必须直接等于目录定义。全部尺寸/主词条生成数据可往返，非法数值被拒绝 |
| 中 | `scripts/spring/spring_save_validation.gd::invalid_field`、`spring_run.gd::save_to_file` | 对比数组与其 duplicate 的长度不能查重，重复/未知队员能读档但下场遭遇无法准备；写档未先检查自身镜像 | 按角色目录检查 ID 与唯一性，保留旧档空编队迁移；写档预检失败保留上一份文件。覆盖合法顺序、旧档、重复/未知角色及原文件保留 |
| 低 | `scripts/persistence/session_save.gd::write`、`play_session.gd::save`、`ui/game_shell.gd::_on_action` | 校验失败没有日志，界面一律暗示磁盘错误，实际排查方向被误导 | 分别报告快照校验失败、文件写入失败和地图保存失败；日志包含字段或阶段；失败继续停留在当前旅程。坏结构诊断不会二次报脚本错误 |

装备数值的校验也覆盖穿戴、背包和队员槽位的全部入口。负装备修正仍合法；角色基础值与最终生命保持原有约束。小数、非有限数、字符串、bool 和溢出整值不会借规范化进入严格快照。

## 持久化与依赖关系

| 模块 | 职责及数据 | 本轮检查结论 |
|---|---|---|
| `SaveFile` | 同目录临时文件、flush 后 rename；原文件在失败前不截断 | 保留原有原子替换机制。双文件提交必须依赖事务日志，不能将单文件原子性视为双文件原子性 |
| `SessionCodec` | JSON 标签保留 int64、Vector2i、Vector2、Color、StringName；不反序列化对象或脚本 | 继续拒绝未知标签、重复键、溢出/非有限数和非法数组；没有把严格类型检查改成自动强转 |
| `SessionSave` / `SessionValidation` | 暂停文件的编码、类型/玩法规则预检、恢复交接 | 战斗和地图都通过同一入口；校验与 IO 失败能区分；既有坏档保留与暂停原地停留测试继续有效 |
| `PlaySession` / `BattleSession` | 场景状态捕获与重建，包括 AP、队伍、各角色属性、预告、状态、动画、RNG 和地图来源 | 新增跨“普通地图 JSON → 战斗 → 严格暂停快照”的端到端覆盖，补齐前次只测试新建装备的缺口 |
| `PartyLoadout` / `SpringBattleBridge` | 独立队员装备与血量、共享背包、地图到战斗的载荷和战后结果 | JSON 边界规范化，内存快照继续严格；从任何合法装备来源进入战斗后都可暂停 |
| `SpringRun` / `SpringSaveValidation` | 地图布局、探索位置/体力、资源、事件、商店、路径、角色生命和待结算记录 | 读写共用预检；重复/未知编队不能成为新存档；旧档空编队及正常 JSON 整值仍有效 |
| `SpringRunStorage` / `SpringSaveTransaction` | 远征与工坊双文件日志、恢复、结算凭证、重复点击幂等 | 继续复验合法有符号装备、pending/prepared、异常镜像、重启与奖励仅一次；本轮没有另建一套结算流程 |
| `AtelierStash` | 残晶钱包、行前打包和配方 | 已有同源读写/事务预检；有限整值、配方目录与失败原文件保留规则无新增合法数据误拒 |
| `SquadLoadoutStore` | 三套持久编队与活动队伍 | 已有目录/唯一性/整数验证；保持既有坏档防覆盖机制，远征自己的队伍副本也补上等价约束 |
| `FragmentCatalog` / `FragmentStore` | 模块生成与数值权威、唯一实例、角色槽位和容量 | 新增可复用镜像预检；读取、邮件恢复使用同一套定义，避免事务绕过正常读档验证 |
| `CommunicationsMailService` / `MailboxValidation` | 邮箱、附件、领取凭证、指定存档模块发放 | 新增嵌套结构预检；日志版本/两份镜像/目标/凭证先检查；失败内存不提前提交，恢复不会重发 |
| `CustomLevelData` / `CustomLevelBridge` | 自定义地图 JSON、设计稿校验与沙盒启动 | 已有整值/坐标/数值/目录边界；其暂停恢复继续走 SessionSave，既有套件覆盖正常设计与坏稿 |
| `GameAudio` / `SpringRegionProgression` | ConfigFile 音频开关与已解锁区域 | 已检查配置读写及失败处理；未发现与本次同类的合法装备/JSON int 误拒；其原子性限制见下方 |

玩家运行时的主要流转为：标题/工坊读取局外钱包与编队 → SpringRun 创建或读取远征 → 地图经 SpringBattleBridge 准备遭遇 → BattleView/Controller 操作单个上场角色 → 战后结果形成 pending，再转 prepared → 事务提交远征和钱包，凭证防止重复奖励。途中暂停则由 BattleSession 或地图捕获完整位置，通过 SessionCodec 写入会话文件；恢复时先验证再重建场景，不能依赖比暂停点更新的地图存档。

运行与验证入口保持不变：Godot 4.7.2 导入项目后运行 `project.godot`；自动验证先 `--headless --path . --import`，再使用 `tests/run_all.ps1` 或 `tests/run_all.sh`，Windows 包用 `tools/build_windows.ps1`。测试必须隔离 `user://`，不能用玩家真实配置目录跑套件。

## 回归证据

- 修复前新增“地图装备进入下场战斗”回归，全部目录装备的保存/重读均失败；修复后覆盖背包换装、切换角色与重建实际场景，逐字段比较角色与 RunState。
- 新持久化契约套件先验证旧代码确实接受错误编队、截断数值及无效事务；修复后同一输入在任何覆盖前被拒绝。进一步复现邮件提前修改内存与旧数据重试重复生成，已钉住并修复。
- 保留既有战后结算 JSON、暂停恢复、编队、残片和通讯终端套件。全量实跑值、逐套件断言与覆盖下限见 [BASELINE](BASELINE.md) 与 `tests/framework/baseline.json`，不在多份文档复制活计数。
- Windows 原生导出、包内容检查、EXE 启动烟测和双端 CI 结果附于实施 PR。原生烟测不替代人工完整游玩签收。

## 仍存在的边界与后续优先级

| 优先级 | 边界 | 原因与后续工作 |
|---|---|---|
| P1 / 人工 | 最新 Windows 包的长局交互验收仍由人工执行 | 自动回放已覆盖具体存档路径，但不能冒充完整人工游玩。继续按 WINDOWS_DELIVERY 检查实际保存退出、返回标题、续玩、换人和结算 |
| P2 / 工程 | 音频和区域解锁配置仍直接使用 ConfigFile.save | 属于既有配置 IO 原子性限制，本轮没有复现文件损坏，也不是此次暂停错误根因。后续可统一为临时文件替换并补断电/写入失败验证 |
| P2 / 运行约束 | 多个游戏进程同时修改同一用户存档没有跨进程锁 | 单次原子替换和事务重试不能代替多进程互斥。若产品正式支持同时多开，需要增加账号/存档写锁和版本冲突处理；本轮仅验证单进程顺序恢复 |
| 保留 / 设计 | 历史生命上限缺少缩放来源时采用保守兼容 | 按既定策略不猜测并覆盖旧血量比例；与本轮类型修复分开。Boss 败北、多回合预告、Android 的暂缓决定也保持原状态 |

不自动删档、重置旅程、移除合法负属性装备，或为了通过保存而把不合法的战斗数据强转成整数。遇到无法验证的历史文件保留原件和日志，交由明确的版本迁移处理。
