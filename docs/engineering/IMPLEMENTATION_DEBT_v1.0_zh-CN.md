# ECHO｜实现欠账清单 v1.0

- **文档性质**：工程文档，不是设计文档
- **唯一职责**：记录「法则 vs 实现」的差距、修法与状态
- **不做什么**：不解释世界规则（那是《系统法则》的事）、不做设计决定
- **维护方式**：**法则新增或修改约束、或代码触及法则相关实现时**，同步更新本文档；常规代码迭代（纯 UI、无关缺陷修复）不必更新

> **为什么单独成文**：这份内容曾作为 §5 塞在《系统法则 v1.0》里，结果每一版代码都让设计文档欠账。法则应该约束实现，而不是描述实现——两者的更新节奏不同，必须分开。

## 二、逐条说明

### D-01｜`K` 未参数化（法则三）

**现状**：`CombatMath.calculate_damage` 内直接写死常数。

```gdscript
return maxi(1, floori(float(raw_damage) * 1000.0 / (1000.0 + float(safe_resistance))))
```

**为什么是欠账**：法则三把 `K` 定义为「抗性的汇率」，是法则的公开参数。写死在公式里，法则三的语义就无法被外部引用。

**修法（两步，可分别验证）**

| 步骤 | 改动 | 验证方式 |
|---|---|---|
| ① | 提取 `const ATTENUATION_K: int = 1000`，替换字面量 | 现有断言应全绿——数值不变 |
| ② | 提供可覆写入口（导出字段或静态传参） | 新增断言：改 K 后透过率按新公式变 |

**边界**：本条修法**止于**让 `K` 可被读取与传参。**关卡层如何接入，归 D-02**——那里建的是通用参数覆写字典。此处不新增专属字段，避免造出一个回头要删的过渡字段。

**修完的直接收益**：跨单位制的抗性从此有唯一答案。百分比减伤 `p` 与整数抗性 `R` 的换算 `R = K × p ÷ (1 − p)` 只在 `K` 可读时才能被引用；在此之前，每个新角色都要手算一遍，且算错了没人发现。

---

### D-02｜无参数覆写载体（法则四）

**现状**：关卡已是数据文件（`data/levels/*.tres`），但字段只有布阵、敌人、障碍，**没有任何法则参数**。

**为什么是欠账**：法则四说「异象 = 覆写已命名的法则参数」。参数没有名字、没有入口，法则四就只是纸面推演。

**修法**：在关卡资源上加一个参数覆写字典，键必须是法则里已声明的参数名（`attenuation_k` / `ap_pool` / `telegraph_lead_turns` / `residue_*`）。**键不存在于法则参数表时应报错，而不是静默忽略**——静默忽略会让异象失效而无人发现。

**优先级**：最高。它是「世界观 → 关卡参数」这条链唯一缺的一环。

---

### D-03｜无残余回响机制（法则一推论）

**现状**：攻击结算后落点不留痕迹。

**为什么是欠账**：按现在的实现，法则一只有「预告」没有「回响」，名不副实。

**修法**：先做成单个单位的专属能力（`residue_lifetime_turns` / `residue_repeat_ratio` 两个参数挂在该单位的数据上），验证手感后再决定是否升为通用机制。**升格前不进关卡异象体系。**

**优先级**：低。属于内容扩展，不阻塞其他工作。

---

### D-04｜法则一的三参数未参数化（法则一）

**现状**：预告提前量、可改写性、锁定方式均为代码内的固定行为，没有名字也没有入口。

**为什么是欠账**：法则一在参数表中声明了它们，实现里却查不到对应的符号。

**修法**：同 D-01 的 ①② 两步——先命名，再暴露。**在 D-01/D-02 的载体建好之前不必单独做**，一起做成本更低。

**优先级**：中。与 D-01/D-02 合并实施。

## 三、非欠账记录

以下内容**不是欠账**，但容易被误读成「法则出错」，必须记录。

### 3.1 参数变更

参数变了不等于法则错了，只记录，不产生欠账。

| 日期 | 参数 | 变更 | 法则是否需改 |
|---|---|---|---|
| 2026-11-25 | `ap_pool` | 3（单角色）→ 5（队伍共享） | **不需要**——法则二不绑定数量 |
| 2026-11-25 | `ap_pool_scope` | 单角色 → 队伍共享 | **不需要**——法则二声明了两种取值 |

> 这正是 v1.1 数值纪律的价值：**行动点从 3 改成 5，法则文档一个字没动。**

### 3.2 未使用的合法分支

**「延后清算」代价分支未被使用（法则二）**

**现状**：法则二允许代价有两种形式——即时支付行动点、延后进入清算期。当前实现几乎只用前者；清算期只在外部支援系统上出现过。

**为什么不算欠账**：法则从未规定「每个技能必须有冷却」，它只声明两种代价形式**可以**存在。实现只用了一种，属于选择，不属于违反。**法则无需修改。**

> v1.0 审计曾把这件事记成「技能冷却不成立」，等同判定法则出错——那是误判，已在此更正。

**待决**：是否在主动技能上引入清算期。这是数值与手感问题，不是法则问题。

## 四、如何核对本表

```sh
tests/run_all.sh        # bash
tests\run_all.bat       # Windows
```

纯文档或纯参数改动不应改变断言总数；断言数变化须在 `docs/engineering/BASELINE.md` 记录原因。

**核对纪律**：静态读代码、测试中存在断言、实际运行通过——三者是不同状态，不得混为一谈。本表只记录第一类的结论，运行验证须另行记录。
